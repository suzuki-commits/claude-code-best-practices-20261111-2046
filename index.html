CLAUDE.md とスキル
書き方と使い分け

毎回ブレずに動かすための、設定と運用の要点。公式ドキュメントに基づき、どこに何を書けばClaude Codeが迷わず動くかを整理しました。

事実は CLAUDE.md、手順はスキル、例外なしは Hook

鈴木章裕　｜　株式会社コミクス 代表取締役　｜　2026年11月5日　公式ドキュメントで確認

資料の要点を見る 自社の運用について相談する

書く場所を3つに分ける

判断の軸は「いつ必要な情報か」。

毎回必要なものだけを常時読み込みに残し、残りは必要なときに読ませる
1

CLAUDE.md

毎回必要な事実と規約（コマンド、注意点）

2

スキル

必要なときの手順（デプロイ、レビュー）

3

Hook など

例外を許さないルール（必ず実行、絶対に触らない）

CLAUDE.md は短く、具体的に

目標は1ファイル200行以内。コードから自明なことは書かない。

書くもの

  • ビルド・テストのコマンド
  • 誤解を招きやすい箇所
  • チームで決めた決定事項
  • 過去に2回以上修正したルール

書かないもの

  • コードを読めば分かること
  • 長い手順（スキルへ移す）
  • 特定ディレクトリ専用のルール（.claude/rules/ へ移す）
基準は「Claude が毎回再発見しがちな情報」か。
詰め込まず、置き場所を分ける（長い手順と専用ルールは CLAUDE.md の外へ）
書きたい内容 置き場所 読み込み
コマンド・規約・注意点 CLAUDE.md 毎セッション
特定ディレクトリ専用ルール .claude/rules/（paths: を指定） 対象を扱うとき
長い手順・チェックリスト .claude/skills/ 使うときだけ
例外を許さないルール Hook・deny ルール（managed settings） 自動で強制

守られる指示の書き方

プロンプトの原則に従うと遵守率が上がる。

1

明示的に書く

「ちゃんとテストする」ではなく
pnpm test path/to/file.test.ts で実行、のように書く

2

「なぜ」を添える

「src/legacy/ のパターンは古いのでコピーしない」のように理由を書く

3

例を示す

「2スペースインデントを使う」「src/lib/errors.ts のヘルパーを使う」

指示は「守れたか確認できる」形で書く

作って終わりにしない

初期生成から監査、変更管理までを回す。

1

生成する

/init で初期ドラフトを作り、不要な行を削る

2

監査する

/doctor prompt-audit（v2.1.283以降）で矛盾や古い指示を確認

3

管理する

所有者を決め、コードレビューと同様に変更を管理する

4

強制する

例外なしのルールは Hook や deny ルールで強制する

「必ず実行」「絶対に触らない」は Hook で仕組みにする

CLAUDE.md / SKILL.md の実例

資料に掲載されているサンプルをそのまま抜粋しています。

CLAUDE.md の最小例

CLAUDE.md
# Commands - Install: pnpm install - Run one test file: pnpm vitest run path/to/file.test.ts - Typecheck: pnpm tsc --noEmit - Lint: pnpm lint # Conventions - エラーは `src/lib/errors.ts` のヘルパーを使う。生の文字列をthrowしない - `src/legacy/` は現役だが、新しいコードにそのパターンをコピーしない - APIハンドラは `src/api/handlers/` に置く # Gotchas - 統合テスト前に `.env.example` を参考に `DATABASE_URL` を設定する - 生成ファイル（`src/gen/`）は絶対に手動編集しない

実践的な例①：概要とコマンド

CLAUDE.md
# プロジェクト概要 Next.js + TypeScript の管理画面。モノレポではなく単一リポジトリ。 # コマンド - インストール: `pnpm install` - 開発サーバー: `pnpm dev` - テスト（単一ファイル）: `pnpm test path/to/file.test.ts` - 型チェック: `pnpm typecheck` - ビルド: `pnpm build`
ポイント：コードから読み取れない情報だけを、短く具体的に書く。

実践的な例②：規約と注意点

CLAUDE.md
# コーディング規約 - コンポーネントは関数コンポーネント + TypeScriptで書く - スタイルはTailwind CSSを使う（CSS Modulesは使わない） - エラーハンドリングは `src/utils/error.ts` の `AppError` を使う - 日付はすべて `date-fns` を使う（native Dateの直接操作は避ける） # 注意点 - `src/legacy/` 配下のコードは参照のみ。新しい実装にコピーしない - 環境変数は必ず `.env.example` に記載する - データベースマイグレーションは `prisma/migrations/` に追加する。既存のマイグレーションファイルは編集しない - テストを追加・修正したら、該当テストだけを実行して確認すること

SKILL.md の書き方の例

SKILL.md
--- name: summarize-changes description: 未コミットの変更を要約し、リスクを指摘する。ユーザーが「何が変わったか」「コミットメッセージを書いて」と頼んだときに使う。 --- # 変更の要約 ## 現在の差分 !`git diff HEAD` ## 手順 1. 上記の差分を2〜3個の箇条書きで要約する 2. エラー処理不足、ハードコード、テスト更新漏れなどのリスクを指摘する 3. 差分が空なら「未コミットの変更はありません」と返す

スキルはフォルダ＋SKILL.md

my-skill/
├── SKILL.md # 必須
├── references/ # 任意：詳細ドキュメント
├── assets/ # 任意：テンプレートなど
└── scripts/ # 任意：実行するスクリプト
用途 置き場所
個人用（全プロジェクト） ~/.claude/skills/my-skill/SKILL.md
プロジェクト用 .claude/skills/my-skill/SKILL.md
補足：必須は SKILL.md だけ。ほかのフォルダは必要になったら足す。

押さえる4つのポイント

最も重要なのは description。

name

小文字・数字・ハイフンのみ。最大64字でフォルダ名と合わせる

description

何をするか＋どんなときに使うかを具体的に。発動の判断材料になる

本文

手順を明確に書く。長くなったら詳細は references/ へ移す

動的コンテキスト

!`コマンド` でコマンド出力をその場で埋め込める

使い方：依頼が description に合えば自動発動。/skill-name で手動も可。

CLAUDE.md と SKILL.md の違い

項目 CLAUDE.md SKILL.md（スキル）
読み込み 開始時に常時（ルート） 名前と説明は常時、本文は都度
消費量 高い（毎回全行が載る） 低い（本文は呼ぶときだけ）
向く内容 事実・規約 手順・チェックリスト
例 コマンド、構成、規約 デプロイ、リリース、レビュー
推奨サイズ 200行以内が目標 本文500行程度まで
場所 プロジェクトルートなど .claude/skills/ など
CLAUDE.md は説明書、SKILL.md は作業マニュアル

迷ったら「いつ必要か」で決める

常に必要な事実は CLAUDE.md、必要なときの手順はスキル。

CLAUDE.md に書くもの（毎回覚えておく前提条件）

  • npm run test の実行方法
  • エラーハンドリングのルール
  • ディレクトリの役割
  • 過去に2回以上修正した注意点

SKILL.md に書くもの（必要なときだけ見る手順）

  • リリース前のチェックリスト
  • 特定形式の文書作成手順
  • デプロイ作業の手順
CLAUDE.md の長い手順は、無関係な作業でもトークンを使う。

よくある質問

資料の内容をもとに、判断に迷いやすい点をまとめました。

CLAUDE.md と SKILL.md はどちらに書けばいいですか？

常に必要な事実（コマンド・規約・ディレクトリの役割など）は CLAUDE.md へ、必要なときだけ見る手順（リリース前チェックリストやデプロイ手順など）は SKILL.md へ分けます。

CLAUDE.md の適切な長さの目安は？

1ファイル200行以内を目標に、コードを読めば分かる内容や長い手順は書かず、スキルや .claude/rules/ へ移します。

絶対に守らせたいルールはどこに書きますか？

「必ず実行」「絶対に触らない」など例外を許さないルールは、CLAUDE.md の文章ではなく Hook や deny ルール（managed settings）で強制します。

SKILL.md を書くときに最も重要な項目は？

description です。何をするか＋どんなときに使うかを具体的に書くことが、自動発動の判断材料になります。

作った CLAUDE.md や SKILL.md はそのままでいいですか？

作って終わりにせず、/doctor prompt-audit（v2.1.283以降）などで矛盾や古い指示を定期的に点検し、所有者を決めて変更を管理します。
